## 二、数据库表设计

推荐系统涉及 **18 张专用表**（`recommendation_init.sql`）+ 业务基础表。

### 2.1 基础业务表（`init.sql`）

| 表名 | 用途 | 推荐系统使用方式 |
|------|------|----------------|
| `users` | 用户基本信息 | 提取 user_sex, following_count, follower_count |
| `videos` | 视频基本信息 | 提取 category, duration, visit_count, likes_count 等 |
| `user_behaviors` | 用户行为流水 | 作为训练数据的 fallback 正样本来源 |

### 2.2 推荐系统专用表（`recommendation_init.sql`）

#### 核心特征表

| 表名 | 字段要点 | 用途 |
|------|---------|------|
| **`user_profiles`** | interest_tags(JSON), category_preference(JSON), avg_watch_duration, avg_completion_rate, like_rate, comment_rate, share_rate, total_view_count, user_level | 用户画像，训练特征中的用户侧特征 |
| **`video_features`** | quality_score, popularity_score, ctr, finish_rate, like_rate, comment_rate, share_rate, avg_watch_duration, exposure_count | 视频特征，训练特征中的视频侧特征 |
| **`author_scores`** | quality_score, influence_score, overall_score, avg_engagement_rate, level | 作者评分，训练特征中的作者侧特征 |
| **`video_hot_scores`** | video_id, time_window(1h/6h/24h/7d), hot_score, rank | 实时热度，召回和排序的上下文特征 |

#### 标签/训练数据表

| 表名 | 字段要点 | 用途 |
|------|---------|------|
| **`recommendation_exposures`** | user_id, video_id, is_clicked, is_liked, is_shared, watch_duration, completion_rate, recall_source, position | **训练标签来源**，记录推荐曝光及用户反馈 |
| **`user_video_interactions`** | click_count, total_watch_time, max_watch_progress, is_liked, is_shared, engagement_score | 详细交互记录，作为曝光数据的 fallback |

#### 召回辅助表

| 表名 | 用途 |
|------|------|
| `tag_video_mappings` | 标签→视频映射，基于标签的内容召回 |
| `category_video_stats` | 分类统计，热门分类召回 |
| `video_similarities` | 视频相似度，相似视频召回 |
| `video_embeddings` | 视频向量嵌入，向量检索召回 |
| `user_embeddings` | 用户兴趣向量，协同过滤 |
| `negative_feedbacks` | 用户负反馈，推荐过滤 |
| `recommendation_bloom_filters` | 布隆过滤器，已曝光去重 |

#### 实验/日志表

| 表名 | 用途 |
|------|------|
| `ab_test_experiments` | A/B 测试实验配置 |
| `ab_test_groups` | 实验分组 |
| `user_ab_test_assignments` | 用户分组分配 |
| `recommendation_request_logs` | 推荐请求日志 |
| `recommendation_model_versions` | 模型版本管理 |

## 三、训练数据生成与清洗

### 3.1 数据来源

训练数据通过 `data_generator.py` 的 `DataGenerator` 类从 MySQL 多表 JOIN 生成。

**核心 SQL 数据流：**

```
recommendation_exposures (标签)
    ├── LEFT JOIN users + user_profiles (用户特征)
    ├── LEFT JOIN videos + video_features (视频特征)
    ├── LEFT JOIN author_scores (作者特征)
    └── LEFT JOIN video_hot_scores (热度特征)
    = 训练 DataFrame
```

### 3.2 标签定义

从 `recommendation_exposures` 表提取 4 个标签：

| 标签 | 来源字段 | 定义 |
|------|---------|------|
| `is_click` | `re.is_clicked` | 用户是否点击了推荐的视频（**主标签**） |
| `is_finish` | `re.completion_rate >= 0.8` | 完播率 ≥ 80% 视为完成观看 |
| `is_like` | `re.is_liked` | 用户是否点赞 |
| `is_share` | `re.is_shared` | 用户是否分享 |

### 3.3 Fallback 机制（无曝光数据时）

当 `recommendation_exposures` 为空时，从 `user_video_interactions` 构建伪曝光数据：

1. **正样本**：从 `user_video_interactions` 取 `click_count > 0` 的记录
2. **二次 Fallback**：从 `user_behaviors` 取 view/like/share 行为
3. **负采样**：随机配对用户-视频组合（4:1 负正比），排除已交互对
4. **去重**：对同一 (user_id, video_id) 保留最新记录
5. **Shuffle**：全量打乱，random_state=42

### 3.4 用户特征提取

```sql
-- 来自 users 表
user_sex, user_following_count, user_follower_count

-- 来自 user_profiles 表
user_avg_watch_duration, user_avg_completion_rate,
user_like_rate, user_comment_rate, user_share_rate,
user_total_view_count, user_level
```

### 3.5 视频特征提取

```sql
-- 来自 videos 表
author_id, category, video_duration,
video_visit_count, video_likes_count, video_comment_count,
video_share_count, video_favorites_count, video_created_at

-- 来自 video_features 表
video_quality_score, video_popularity_score,
video_avg_watch_duration

-- 注意: video_ctr, finish_rate, like_rate 等从 DENSE_FEATURES 中移除
-- 原因: 这些字段是由 is_click 等标签聚合而来，会导致标签泄露(label leakage)
```

### 3.6 作者特征提取

```sql
-- 来自 author_scores 表
author_quality_score, author_influence_score,
author_overall_score, author_avg_engagement_rate
```

### 3.7 上下文/热度特征

```sql
-- 来自 video_hot_scores 表 (取 time_window='24h')
video_hot_score
```

## 四、特征工程

由 `feature_engineering.py` 的 `FeatureProcessor` 类完成，分为三大类特征。

### 4.1 稀疏特征（Sparse Features）

7 个类别特征，使用 LabelEncoder 编码后送入 Embedding 层：

| 特征名 | 来源 | 说明 |
|--------|------|------|
| `category` | videos.category | 视频分类：美食/旅行/科技/搞笑/健身/音乐 |
| `user_sex` | users.sex | 用户性别 |
| `user_level` | user_profiles.user_level | 用户活跃等级 1-5 |
| `video_duration_bucket` | 由 video_duration 分桶生成 | 时长桶：0-15s/15-30s/30-60s/1-2m/2-5m/5-10m/10m+ |
| `hour_of_day` | exposure_time 提取 | 曝光小时 0-23 |
| `day_of_week` | exposure_time 提取 | 星期几 0-6 |
| `device_type` | 默认 mobile | 设备类型 |

### 4.2 哈希桶特征（Hash Bucket Features）

高基数 ID 特征，使用哈希取模控制 Embedding 大小：

| 特征名 | 桶大小 | 说明 |
|--------|--------|------|
| `user_id` | 500 | 用户ID 哈希 → [0, 499] |
| `video_id` | 500 | 视频ID 哈希 → [0, 499] |
| `author_id` | 200 | 作者ID 哈希 → [0, 199] |

### 4.3 稠密特征（Dense Features）

23 个连续数值特征，使用 MinMaxScaler 归一化到 [0, 1]：

| 类别 | 特征列表 |
|------|---------|
| 用户画像 (8个) | user_avg_watch_duration, user_avg_completion_rate, user_like_rate, user_comment_rate, user_share_rate, user_total_view_count, user_following_count, user_follower_count |
| 视频特征 (8个) | video_quality_score, video_popularity_score, video_avg_watch_duration, video_duration, video_visit_count, video_likes_count, video_comment_count, video_share_count, video_favorites_count |
| 作者特征 (4个) | author_quality_score, author_influence_score, author_overall_score, author_avg_engagement_rate |
| 上下文特征 (2个) | video_freshness_hours, video_hot_score |
| 派生特征 (3个) | user_video_duration_ratio（用户平均观看/视频时长）, user_activity_log（log1p(总观看数)）, video_popularity_log（log1p(播放量)） |

### 4.4 序列特征（DIN 模型专用）

| 特征名 | 来源 | 说明 |
|--------|------|------|
| `hist_video_ids` | user_behaviors 表 | 用户最近 50 个 view/like/share 的视频 ID 序列 |

### 4.5 数据清洗规则汇总

1. **缺失值处理**：稀疏特征 fillna("unknown")；稠密特征 fillna(0.0)
2. **未见类别处理**：LabelEncoder 训练时加入 "unknown"，推理时未见值映射为 "unknown"
3. **标签泄露防护**：从 DENSE_FEATURES 中移除了 video_ctr/finish_rate/like_rate 等从标签聚合的字段
4. **去重**：曝光数据按 (user_id, video_id) 去重，保留最新记录
5. **负采样比例**：正:负 = 1:4，最多 10 万条负样本
6. **Train/Val 划分**：fit_transform 只在训练集上 fit，避免验证集数据泄露

## 五、模型训练

### 5.1 训练框架

- **框架**：TensorFlow 2.x + DeepCTR 库
- **训练脚本**：`DeepCTR/tiktok_rec_service/train.py`
- **命令**：`python3 train.py --model deepfm --days 30 --output ./models`

### 5.2 支持的模型

#### DeepFM（已训练，当前线上模型）

```
结构: FM（二阶特征交叉） + DNN（高阶特征交叉）
隐层: (128, 64)
Dropout: 0.2
L2正则: 1e-5
损失函数: binary_crossentropy
主标签: is_click
```

**训练结果：**
- 训练样本：23,874 / 验证样本：5,969
- 正样本比例：8.0%
- **验证集 AUC：0.6399**
- **验证集 LogLoss：0.2656**

#### DIN（Deep Interest Network）

```
结构: Attention 机制捕捉用户兴趣序列
序列特征: hist_video_ids (最近50个交互视频)
Attention: (64, 16) + Dice 激活
隐层: (128, 64)
主标签: is_click
```
> 需要丰富的用户行为序列数据，当前未训练。

#### MMoE（Multi-gate Mixture-of-Experts）

```
结构: 多门控混合专家网络（多任务学习）
专家数: 3
专家维度: 64
任务: is_click(权重1.0), is_finish(0.8), is_like(0.5), is_share(0.3)
Tower: (64, 32) per task
```
> 需要多任务标签数据，当前未训练。

### 5.3 训练配置

| 参数 | 值 | 说明 |
|------|-----|------|
| batch_size | 256 | 批大小 |
| epochs | 50 | 最大训练轮数 |
| learning_rate | 1e-3 | Adam 优化器学习率 |
| early_stopping_patience | 8 | 验证指标 8 轮不提升则停止 |
| validation_split | 0.2 | 20% 数据用于验证 |
| train_days | 30 | 使用最近 30 天数据 |

训练完成后保存到 `models/` 目录：

```
models/
├── deepfm_weights.h5         # DeepFM 模型权重
├── deepfm_best.h5            # 最佳 checkpoint
```


### 6.4 在线推理流程

```
1. 收到 (user_id, video_ids) 请求
2. DataGenerator.generate_prediction_data() 从 MySQL 实时查询特征
   - JOIN users + user_profiles → 用户特征

   - JOIN video_hot_scores → 热度特征
3. FeatureProcessor.transform() 特征变换（复用训练时的 encoder/scaler）
4. model.predict() TensorFlow 推理
5. 按 score 降序返回
```

## 七、Go 侧推荐链路

### 7.1 启动链路

`recommendation_agent_starter.go` 中的 `StartRecommendationAgent()` 按顺序初始化：

```
1. RealtimeStateService  → 感知层（用户实时状态）
2. UserProfileService    → 用户画像服务
3. RecommendationEngine  → 多路召回引擎（6 策略）
4. IntegratedEngine      → 集成推荐引擎（召回→粗排→精排→重排）
5. CTRServiceClient      → Python CTR 服务客户端
6. HotScoreService       → 视频热度计算
7. RecommendationAgent   → 决策 Agent（统领全局）
```

### 7.2 RecommendationAgent 决策逻辑

Agent 采用 **感知-决策-执行** 三阶段架构：

**感知阶段（Perceive）：**
- 查询 `user_profiles` 获取用户参与度
- 查询 `RealtimeStateService` 获取连续跳过次数、聚焦话题等
- 计算 engagement_score, action_count

**决策阶段（Decide）：**

| 条件 | 决策 | 说明 |
|------|------|------|
| action_count == 0 | COLD_START | 新用户，无历史行为 |
| consecutive_skips > 阈值 | HOT_EXPLORE | 连续跳过太多，切换到热门 |
| focused_topic != "" | TOPIC_DEEP_DIVE | 用户深度关注某话题 |
| 其他 | STANDARD | 标准推荐流程 |

**执行阶段（Execute）：**

- **COLD_START**：只用 hot_video + new_video 召回 → 粗排（跳过 CTR 精排）
- **STANDARD**：全链路 6 路召回 → 粗排 → CTR 精排 → MMR 重排
- **HOT_EXPLORE**：HotScoreService 热门召回 → 粗排
- **TOPIC_DEEP_DIVE**：特定话题召回 → 全链路

### 7.3 多路召回策略

| 策略 | 数据来源 | 说明 |
|------|---------|------|
| `hot_video` | Redis `hot:video:*` + MySQL `video_hot_scores` | 热门视频召回 |
| `new_video` | Redis `videos:timeline` + MySQL `videos` | 最新视频召回 |
| `content_based` | Redis 用户画像 + MySQL 标签/分类 | 基于内容的召回 |
| `collaborative_filtering` | Redis/MySQL 用户行为矩阵 | 协同过滤 |
| `social` | MySQL 关注关系 | 社交关系召回 |
| `similar_video` | MySQL `video_similarities` | 相似视频召回 |

### 7.4 粗排（EnhancedRankingModel）

基于 Redis 用户画像和视频特征的加权打分模型，权重配置：

| 特征类别 | 权重分配 |
|---------|---------|
| 视频质量（CTR/完播率/点赞率等） | 50% |
| 交叉特征（用户-作者亲和/分类匹配/标签重叠） | 24% |
| 时效性（新鲜度/热度/趋势） | 16% |
| 用户特征（活跃度/观看时长/互动率） | 8% |
| 上下文（时段/设备/网络） | 4% |

最终通过 Sigmoid 激活输出 [0, 1] 分数。

### 7.5 精排（CTR Service 调用）

`ctr_client.go` 的 `CTRServiceClient` 通过 HTTP 调用 Python 服务：

```go
POST http://localhost:8000/predict
Timeout: 2000ms
Fallback: 返回默认分数 0.5
健康检查: 每 10 秒 GET /health
```

### 7.6 重排序（MMR 多样性）

使用 **Maximal Marginal Relevance** 算法平衡相关性与多样性：

```
MMR(D) = λ × Score(D) − (1−λ) × max(Similarity(D, Di))
λ = 0.7 (偏向相关性)
```

同时应用 Thompson Sampling 探索策略（exploration_ratio = 10%）。

## 八、系统打通方式

### 8.1 Go ↔ Python 通信

Go 后端通过 HTTP REST API 调用 Python CTR 服务：

```
Go (Kitex Video Service :8891)
  └── CTRServiceClient (ctr_client.go)
        └── HTTP POST → Python FastAPI (serve.py :8000)
              └── TensorFlow DeepFM 推理
```

### 8.2 数据流打通

```
MySQL (TikTok 数据库 :3307)
  ├── Go 侧: GORM 直接查询 → 召回/粗排
  ├── Python 训练: SQLAlchemy/PyMySQL → data_generator.py → train.py
  └── Python 在线: PyMySQL → serve.py (实时查特征)

Redis (:6379)
  ├── Go 侧: 用户画像缓存、热度缓存、布隆过滤器
  ├── 粗排: Pipeline 批量查询用户画像 + 视频特征
  └── 热度同步: HotScoreService 每分钟同步到 Redis
```

### 8.3 服务启动顺序

```bash
# 1. 基础设施（Docker Compose）
docker-compose up -d   # MySQL, Redis, etcd, MinIO, Jaeger

# 2. 初始化数据库
make init-db           # 基础表
make init-rec-db       # 推荐表
mysql < scripts/seed_recommendation_testdata.sql  # 测试数据

# 3. 训练模型
cd DeepCTR/tiktok_rec_service
python3 train.py --model deepfm --days 30

# 4. 启动 Python CTR 服务
python3 serve.py       # :8000

# 5. 启动 Go 微服务
make build
make users             # User Service
make videos            # Video Service (内含推荐 Agent)
make api               # API Gateway :8888
```

## 九、测试数据

## 十一、今日修复记录

### Bug 1: Redis nil pointer panic

**问题**：`IntegratedRecommendationEngine` 中 `NewEnhancedRankingModel(nil, nil)` 未传入 Redis 客户端，导致粗排时 `ltr.redis.Pipeline()` panic。

**修复**：
1. 修改 `NewIntegratedRecommendationEngine` 签名，增加 `redisClient` 和 `database` 参数
2. 在 `recommendation_agent_starter.go` 中传入实际的 Redis 和 DB 实例
3. 在 `getUserProfile` 和 `batchGetVideoFeatures` 中增加 nil 安全检查

### Bug 2: CTR 服务超时

**问题**：默认 200ms 超时不够，TensorFlow 推理 + MySQL 特征查询约需 170ms，30 个视频批量推理容易超时。

**修复**：将 `CTRTimeout` 从 200ms 调整为 2000ms（本地开发环境）。
